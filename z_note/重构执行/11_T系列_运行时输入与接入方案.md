## 1. 总则

**目标**：每模型的全部运行时输入，都能由自己的 adapter 从 raw + splits + 元数据注册表生产，并被自己的模型代码消费；训练（学习型）/ 拟合（优化型）可运行。

**验收标准**：

- T1（AnysoleWorkspace 侧）：每个运行时输入有 producer（脚本/函数）、artifact.json、源 hash、消费端读取测试。
- T2（Baselines 侧）：每处模型改动 = 登记表条目 + 一次提交 + 证据测试；`git diff 111220c -- <模型>` 恰好等于该模型登记条目。
- T 系列总 gate：每模型 one-batch train（学习型）/ one-frame fit（优化型）smoke 通过。

**原则**：

1. 谁消费谁生产——除 raw 数据与 splits 外，中间产物由消费方自产（T1-0a/b 的两处例外已由用户裁定，见 §2）。
2. 偏离原生 = 登记表条目（缘由 + 证据）先行或同提交。
3. D 系列裁定生效：SMPL-24 neutral + 10 betas、BVH-23 / Y-X-Z / cm / 120Hz、40Hz 交付帧率、raw 原样交付（SMPL y-up/m、BVH cm）、每日期标定 json。

## 3. D1 补充：MotionPRO smpl.npy GT 契约（T 系列开工前补录）

2026-09-28 补录：D 系列原始数据适配的遗漏项——MotionPRO 的 smpl.npy 监督文件契约。
（本节先固化已核实的契约与缺口；用户续补内容见 §3.4。）

### 3.1 smpl.npy 是什么

- **不是 SMPL 模型本体**。模型本体 = `SMPL_NEUTRAL.pkl`（v_template / shapedirs / posedirs /
  J_regressor），由 `lib/util/gen_{kps,contact,image_feature}.py` 用 `smplx.create(...)` 加载做 FK/LBS。
- **是每 session 的 GT 监督参数序列**（`lib/dataset/image_pressure.py:39,45,84-87`）：
  `np.load(..., allow_pickle=True).item()` 读出的 dict，与 `feature_hrnet.pth` 同目录配对存在。
- 任何真实动作的 SMPL 参数都必然是**拟合产物**（上游数据集自带的那份也是上游拟合的）；
  我们的拟合源 = raw `motion_neutral_smpl.npz`（动捕 MoSh 拟合，AMASS 风格）——生产链做的是
  **换算 + 时间对齐，不是重新拟合**。

### 3.2 目标格式四键（native 锁死）

| 键 | 形状 | 来源（raw npz 字段） | 注意 |
| --- | --- | --- | --- |
| betas | (10,) | betas | 训练时 repeat window_length（image_pressure.py:84） |
| body_pose | (T, **69**) | **`poses[:, 3:]`** | ⚠️ **不要取 `pose_body` 字段（它是 (T,63)）**；theta (N,72) = global_orient(3) + body_pose(69)（SMPL-24 的 23 个 body 关节） |
| global_orient | (T, 3) | poses[:, :3] | — |
| transl | (T, 3) | trans | 根平移 |

- beta 无直接监督（pred_beta 死输出），但 `train_frappe.py:156` 前向用 GT beta 过 SMPL
  → smpl.npy 必须含 betas。
- 轴系：raw y-up/m（D4 修正后契约）直读，本地适配管线**无需轴转换**——loss_2d_joint 取
  [x,z] 水平分量即按 y-up 口径（原生上游为 z-up，见 §4.1）；gender='neutral' 与
  SMPL-24 neutral 契约（D1）一致。

## 4. T1-A 设计：MotionPRO 虚拟触觉毯

### 4.1 原生地毯契约（`lib/util/gen_contact.py` 实测）

```python
scale = 2.0 / pressure.shape[1]          # 2m / 160 = 1.25cm/px
carpet_pos[i,j,0] = i*scale + 0.5*scale   # x ∈ [0, 1.5m)（120 格轴，毯宽）
carpet_pos[i,j,1] = -j*scale - 0.5*scale  # y ∈ (-2m, 0]（160 格轴，毯长，负向）
carpet_pos[i,j,2] = 0.                    # 地面平面 z=0（原生世界系为 z-up）
```

- 毯 **1.5m×2.0m**：`carpet_pos` 为 (120,160,3)——120 格轴（x）跨度 119×1.25cm≈1.49m、
  160 格轴（y）跨度 159×1.25cm≈1.99m（1.25cm/px）；**固定在世界系**（"joint pos and carpet pos
  are in the same coordinate system"）。
- 索引与轴系注意：压力图形状为 (num_frame, 160, 120) 即 (y,x) 序，且原生查询前对图像做了
  180° 翻转（`cv2.flip(pressure_,1)`+`cv2.flip(pressure_,0)`）——虚拟毯把格点 (i,j) 的足印压力
  画入压力图 `[j,i]` 即可与原生判据自洽；raw SMPL 为 y-up/m（D4）而毯在 z-up 世界系，
  投影前需按 D4 把动捕换算到 z-up/m。
- **虚拟毯尺寸裁定（09-28 用户）**：测试场地为 1.5m 宽 × 4m 长（必然越界），MotionPRO 输入的
  触觉向量**长度 ×2、宽度不变** → 虚拟毯 = **(T, 320, 120)**，1.25cm/格，覆盖 4m（长轴，
  对应原生 160 轴）× 1.5m（宽轴，对应原生 120 轴）；长轴格点语义
  `y_j = -(j×1.25cm + 0.625cm), j=0..319`（原生 `scale=2.0/shape[1]` 硬编码公式按长轴 4m
  语义扩展）。模型入口 bilinear 96×96 不变；消费端断言 (T,160,120)→(T,320,120) 随 T2 登记
  （MotionPRO #4 当前行为改写）。越界帧不标记：足印落在毯外的部分不画入，毯上无触觉信号即可。
- 原生消费逻辑：每帧 SMPL 脚关节 10/11 → `compute_point_with_min_distance` 最近毯格 → 该格 **±3px（RADIUS=3）** 区域 → 区域内压力求和 > 100 判接触 → 输出 (T,4)。
- 结论：原生管线本就做"动捕脚轨迹 → 地毯格点映射"，只是消费物理毯的压力图。我们的虚拟毯 = 把这条链反向：**用同一映射把鞋垫压力画到虚拟毯上**。

### 4.2 虚拟毯生产链

```text
动捕脚轨迹（BVH/SMPL，shared mocap 网格）
  → 脚关节 10/11 世界坐标（y-up/m → z-up/m，D4 契约）→ 投影到毯平面（原生最近格点语义）
  → 鞋垫 48 格压力按足印几何铺展到毯上（脚朝向决定 4×12 的毯上朝向；V2：宽 12cm/4 行、长 24cm/12 列；按毯 (y,x) 索引画入）
  → 合成 (T, 320, 120) 虚拟毯压力图（长轴 4m × 宽轴 1.5m，1.25cm/格）
  → 闭环验证：虚拟毯喂回原生 ±3px/求和>100 接触判据，与动捕接触标签一致
```

生产者：`AnysoleWorkspace/tool/adapters/MotionPRO/`（替代现行 `rasterize_feet` 固定左右块方案——登记表 MotionPRO #4 的"当前行为"改写为本设计）。
