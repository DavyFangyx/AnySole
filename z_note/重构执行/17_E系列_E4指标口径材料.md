## 1. foot sliding：单一公式、两套关节集（结论：已对齐，可跨协议比较）

### 1.1 唯一实现

`anysole/utils/metrics.py:364 foot_sliding_joints(predicted_foot_joints, target_foot_joints, times, *, contact_speed_m_s=0.3)`

- **接触帧判据**：`gt_displacement / dt < 0.3 m/s`，**只看 GT**（`metrics.py:390`），与模型输出、触觉、模板、shape 全无关 → 对所有模型是同一规则、无自由度。
- **指标值**：接触对的**预测**位移均值 × 1000 mm（`metrics.py:392`）。
- **接触判定是逐 (帧,关节) 的**（`contact` 形状 `(T-1, K)`，K=4），`pred_displacement[contact].mean()` 在全部 (帧,关节) 对上取均值；返回 `(值, 接触对数)` 供加权汇总。
- 顶点版 `foot_sliding_vertices`（`metrics.py:395`）是 **SMPL-only 诊断**（默认足部顶点 `3216/3387/6617/6787`），只出现在 AnySole 明细，**不是公共指标**。

### 1.2 两套关节集（协议决定）

| protocol | 关节名（`Baselines/utils/protocols.py:77-80 PROTOCOL_FOOT_NAMES`） | 索引来源 | 语义 |
| --- | --- | --- | --- |
| `smpl24` | `left_ankle, right_ankle, left_foot, right_foot` | `anysole/types.py:201 ANKLE_FOOT_JOINTS`（按名字取 index，与前者**逐字同序**） | 踝 + 足（足部关节在 SMPL 命名里是足尖侧） |
| `bvh23` | `LeftFoot, RightFoot, LeftToeBase, RightToeBase` | `solver._foot_joint_indices(names, protocol)`（缺失即报错，不静默兜底） | 踝（Foot）+ 趾（ToeBase） |

- **位置对应关系**：`left_ankle↔LeftFoot`、`right_ankle↔RightFoot`、`left_foot↔LeftToeBase`、`right_foot↔RightToeBase` —— 两侧都是「每足 2 点（踝、趾/足）」，语义层级一致。
- **消费端一致性**（实测）：
  - 主模型：`anysole/utils/eval_protocol.py:385-386` → `foot_sliding_joints(pred[:, ANKLE_FOOT_JOINTS], gt[:, ANKLE_FOOT_JOINTS], times)`。
  - 基线：`Baselines/utils/solver.py:32` 直接 `from anysole.utils.metrics import foot_sliding_joints`（**同一函数对象**），`:358` 传 `p[:, foot_ids]`，`foot_ids` 由 `_foot_joint_indices` 按 protocol 解析。
  - → **主模型与基线用同一公式实现、同一接触判据（0.3 m/s）、按协议取各自关节集**。可比较性成立。

### 1.3 两处需要在文档里写明的口径细节

1. **接触帧集合跨协议不同**：SMPL-24 行用 SMPL GT 的踝/足速度判接触，BVH-23 行用 BVH GT 的 Foot/ToeBase 速度判接触 → 两条协议行的 `foot_sliding_mm` **分母（接触对数）不同**，是"同公式、不同样本总体"。R_Test2 表把两种 protocol 并列（表内有 protocol 列），因此该列跨协议取值**不应作"谁更稳"的直接排名**，建议在 README/表注写明。
2. **权重**：`(T-1,K)` 对级平均后按 `count` 做跨 session 加权（`accum.add_scalar(..., count)`），main 与 baseline 两侧同式（`solver.py` 与 `eval_protocol.py` 都返回 `(value, count)`）。

### 1.4 前置依赖状态

foot sliding **不依赖 ckpt/数据缺口**：其 GT（接触帧）来自 GT 轨迹本身，主模型与 Step2Motion/MotionPRO 的既有产物已可算。
唯一相关历史缺口（指标文档 §10.2-3）：公共关节版 `foot_sliding_mm` 在**历史 JSON** 中空缺，需各模型重新 eval/导出后回填——属 E 阶段自然回填，不是阻塞项。

## 2. U7：pressure_toolkit 的 PVE（`pve_mm`）启用 vs 禁用

### 2.1 两版口径

| | **版本 A（启用，= 当前代码）** | **版本 B（禁用，= 旧任务书 01 §4.6/§7）** |
| --- | --- | --- |
| 依据 | 2026-09-27 **生成清单裁定**：pressure_toolkit 的 pose/shape/表面属其拟合 pipeline **原生生成** → PVE 可评估（`r_test2_compare.py:ANYSOLE_*` 上方注释原文；`export_baseline_motion.py:216-220` 注释） | `01_统一指标求解器与模型能力任务书.md:14/167/223/269`：pressure_toolkit **不报告**公共 `pve_mm` 及任何 shape/vertex 指标 |
| 注册表 | `MMVP_pressure_toolkit`：`surface/predicted_surface/predicted_shape: true`，`sources: method_optimization` | 应改为 `surface/predicted_surface/predicted_shape: false` |
| 导出元数据 | `surface_source=method_optimization`、`shape_source=method_optimization`、`public_surface_metrics="true"` | `surface_source=template_reconstruction`、`shape_source=method_fitting`、`public_surface_metrics=false` |
| 评测闸门 | `evaluate.py:238` 默认 true → 计算 `pve_mm` | 显式 false → `reasons["pve_mm"]="not_applicable: archive public_surface_metrics=false"` |

### 2.2 旧禁令的**理由**已不成立（关键判断）

01 任务书 §4.6（:177）原话：**「禁止使用 GT beta 重建 pressure_toolkit 网格来获得公共 PVE，因为这评估的是人为替换后的表面，而不是该方法的真实 shape/mesh 输出。」**

实测当前导出链（`export_baseline_motion.py:161-220`）：`shape = data["shape"]`（11 维 = scale+10 betas）、`model_scale_opt = data.get("model_scale_opt", shape[:1])`、`body_pose/global_rot/transl` 全部取自逐帧 `smpl_*.npz`（即**该拟合方法自己的输出**），随后 `model.update_shape()` + `model.update_pose()` 前向得顶点。
→ **没有任何 GT beta 参与**；旧禁令针对的"人为替换表面"在当前链路中不存在。（R1 附带发现：其初值来自 CLIFF 视觉前端，不是 GT。）

### 2.3 但启用会带来一个**可比性**问题（必须在表注里处理）

pressure_toolkit 与 VP-MoCap 都是**拟合/优化族**：其表面是把观测（触觉 / 图像+点云）与 SMPL 先验对齐后的结果，**不是**从条件回归出的表面。MotionPRO 的表面是其解码器输出（预测族）。
→ 启用后 `pve_mm` 列会同时含"预测族"与"拟合族"数值，**排名语义不同**。
且 01 任务书 :179 明确：「**其他 SMPL 模型是否报告 PVE，依据其已批准协议和真实输出能力分别判定，不能从 pressure_toolkit 的裁定外推。**」→ 该列不能靠"一刀切"处理。

### 2.4 影响面（若拍 A，登记；若拍 B，改动）

| 位置 | 影响 |
| --- | --- |
| `results/baselines/pressure_toolkit/metrics/test_comparison.json` | A：含 `pve_mm` 值；B：`pve_mm` 缺省 NaN + `metric_reasons` 记原因 |
| R_Test2 `comparison_summary.{csv,png}` / 逐 session CSV | A：该行 pve 单元格有数；B：显示 `—` |

| VP-MoCap / MotionPRO 行 | A 下同样有值（二者 archive **无** `public_surface_metrics` 元数据，走 `evaluate.py:238` 的**默认 true**）；B 若只改 pressure_toolkit 会造成"同族不同待遇"，需一并裁定 |
| 重跑成本 | **零**：pressure_toolkit 统一导出当前 0/36（C1 未完成），裁定随 C1/D 阶段一并生效，无需返工 |
| 全局开关 | 05 清单 F1 命令带 `--surface-metrics`（开启）；`--no-surface-metrics` 会让全列 `—`（第三种状态，需知悉） |

### 2.5 建议

**拍 A（启用）**，并附三条：
1. 在表注/README 标注 `pve_mm` 为「表面类指标，含拟合族与预测族，跨族不作排名」；
2. 三个 SMPL-24 基线**统一补齐 provenance 元数据**（现在只有 pressure_toolkit 写了 `surface_source/shape_source/public_surface_metrics`；MotionPRO 与 VP-MoCap 缺失，靠默认 true 通过闸门——这本身是隐患，见 E2 §4 附注）；
3. 若要"更严"的备选：把 `pve_mm` 从**公共比较表列**降为**各模型明细**（不删计算、只删表列）——与 AnySole 侧 `pve_mm ∈ DIAGNOSTIC_KEYS` 的处理对称，且回避跨族排名问题。此备选可作为 B 的温和变体。

## 3. 跨 session 尺度对齐（D7 建议的落地状态）

- **D7 结论（doc 10）**：跨 session 值域漂移仅发生在峰值（右脚 cell 35 单通道间歇故障），bulk 稳定（q10–q90 仿射拟合 R²=0.9989）；**尺度对齐勿用 max/p99**（被故障格劫持），**改用非零均值 / p90**；格级过滤判据 = ON 帧 CV<0.4 + 连续 ON>10 帧 + 该格 max>3×同脚其余格 p99。
- **落地状态（实测）**：代码中**未见**基于 max/p99 的跨 session 尺度对齐实现（`grep p99/percentile` 仅命中 `metrics.py` 的 bootstrap 置信区间与 `build_metadata.py:305` 的 sigmoid 分位统计）；`fpp/build_metadata.py:305` 用的是 p90−p10 类稳健量，方向与建议一致。
- → 该项属**登记型**建议：无需改码；但任何后续"按 session 归一化"的实现必须走非零均值/p90，且不得触故障格（与 E3 Q3 同源）。
